## Context

Мотивация — в `proposal.md`, требования — в дельта-спеках. Здесь только то, что нужно, чтобы объяснить подход.

Настройки чата уже живут строкой в `chats`: расписание, окно, категории, признак активности. Публикация идёт одним местом — `GroupQuizService.publish`, которое вызывают и задача расписания, и ручной запуск из кабинета.

Ограничения Telegram Bot API, которые формируют решение:

- перечислить темы форума нельзя: методов чтения списка тем в Bot API нет, есть только создание и правка;
- `message_thread_id` приходит в составе сообщения, отправленного в теме, и больше ниоткуда;
- название темы по её идентификатору не читается: методов чтения тем в Bot API нет, имя приходит только со служебными `forum_topic_created` и `forum_topic_edited` либо в `reply_to_message` команды, отправленной ответом на стартовое сообщение темы;
- `sendPoll` принимает `message_thread_id`; отправка в удалённую или закрытую тему отклоняется ошибкой запроса;
- у сообщения из общей ленты форума `message_thread_id` отсутствует.

## Goals / Non-Goals

**Goals:**

- Ветка задаётся без ручного ввода идентификаторов: администратор физически находится в нужной теме.
- Недоступная ветка не приводит к потере вопроса и не отключает чат.
- Публикация остаётся одним местом: адресование в ветку не расползается по вызывающим.

**Non-Goals:**

- Список тем в кабинете. Bot API его не отдаёт, а собирать по увиденным сообщениям — неполный и зависящий от privacy mode суррогат.
- Несколько веток на один чат. Одна ветка покрывает задачу; несколько потребовали бы отдельной таблицы и правил распределения вопросов между ними.
- Создание темы ботом. Администратор выбирает существующую.

## Decisions

### Ветка — два поля в строке чата, а не отдельная таблица

`message_thread_id` и название темы кладутся в `chats` рядом с остальными настройками чата. Ветка у чата ровно одна, живёт ровно столько же, сколько подключение, и снимается вместе с ним каскадом.

Название хранится потому, что показать в кабинете голый `message_thread_id` мало о чём говорит, а спросить имя у Telegram нечем — читающих методов для тем в Bot API нет.

Отсюда же его необязательность: имя берётся, когда оно пришло вместе с командой, а иначе ветка обозначается номером темы. Требовать от администратора отвечать командой на стартовое сообщение темы ради имени — худший размен: привязка перестала бы работать в самом простом случае ради косметики.

Альтернатива — таблица тем чата — оправдана только при нескольких ветках, а это вынесено в Non-Goals.

### Ветка берётся из сообщения, а не вводится

Команда привязки читает `message_thread_id` своего сообщения. Отсутствие поля означает общую ленту — то же самое сообщение служит и привязкой, и сбросом, отдельной команды сброса не нужно.

Альтернатива — ввод идентификатора в кабинете — отвергнута: администратору пришлось бы доставать число из ссылки на сообщение, и ошибка в нём обнаружилась бы только при следующей публикации.

Подключение чата подчиняется тому же правилу: `/connect`, отправленный в теме, сразу задаёт ветку. Иначе типовой сценарий требовал бы двух команд подряд в одном месте.

### Кабинет только показывает и сбрасывает

Задать ветку из кабинета нечем — там нет `message_thread_id`. Кабинет показывает название и даёт кнопку сброса на общую ленту: это единственные две операции, для которых у него есть данные.

### Отказ Telegram по ветке — снятие ветки и повтор в общую ленту

`publish` разбирает ошибку отправки: если она про недоступную тему, ветка снимается, опрос уходит в общую ленту, администраторы получают уведомление тем же путём, что и при пустом банке.

Альтернатива — считать чат недоступным и отключать его, как при `ChatUnavailableError`, — неверна: чат жив, недоступна только тема, и отключение остановило бы викторину целиком из-за удалённой ветки.

Спека требует опубликовать вопрос, а не пропустить его: иначе удаление темы тихо съедало бы по вопросу за интервал до тех пор, пока кто-нибудь не заметит.

## Risks / Trade-offs

- **Название темы известно не всегда и устаревает.** У команды, просто набранной в теме, имени нет; а если тему переименовали, сохранённое имя устареет, потому что спросить новое неоткуда → идентификатор в обоих случаях верен и публикация не страдает; кабинет показывает номер темы вместо имени, а имя обновляется при следующей привязке.
- **Отказ Telegram по недоступной теме неотличим по коду от других ошибок запроса** → разбор идёт по тексту ошибки, как уже сделано для правки якоря в личке; при неузнанной ошибке поведение прежнее — публикация не состоялась, чат не тронут.
- **Повторная отправка после снятия ветки удваивает обращения к Telegram** на той публикации, где тема отвалилась → случай разовый, дальше ветки нет и запрос один.
- **Привязка в теме требует, чтобы бот эту команду увидел.** При включённом privacy mode бот получает команды в группе, но не обычные сообщения → привязка сделана командой именно поэтому.

## Migration Plan

Миграция добавляет в чат идентификатор и название ветки публикации. Данных для переноса нет: у подключённых чатов ветка пуста, и они продолжают публиковать в общую ленту ровно как раньше.

Откат — обратная миграция; чаты возвращаются к публикации в общую ленту без потери расписаний и статистики.
